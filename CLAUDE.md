# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Photo Dojo: Revival: a browser-only 2D fighting game. Fighters are built on the computer in the Character Studio (`/studio`, `studio.html`): live pose tracking, auto-capture, background removal and sprites run there, on a camera that is either the computer's own (webcam, USB, Continuity Camera) or a phone. The phone (`/capture`, `capture.html`) is only a camera: it streams video to the studio over WebRTC and sends full-resolution stills on request; it runs no models. The game (`/`, `index.html`) is a Phaser app on the same computer and reads fighters from IndexedDB (phones opening `/` or `/studio` get a "this is the big screen / use this phone as the camera" page instead: `src/game/device-gate.ts`). `/about` (`about.html`) is a static About / privacy / FAQ / credits page. No accounts, no backend storage: fighters live in IndexedDB. The only server code is a Cloudflare Worker in `worker/` that relays SDP/ICE (and optionally issues TURN credentials) and stores nothing.

Design docs: `PLAN.md` (overall architecture and data model), `docs/character-studio.md` (the studio, the phone camera and its protocol, fighter sources and editing — implemented; supersedes PLAN §4/§5), `docs/fighting-mechanics.md` (frame data and the reasoning behind the fight rules — implemented), `docs/manual-test.md` (checks needing a real phone/gamepad/network). README.md has the player-facing controls and move list.

## Commands

```sh
npm install && npm install --prefix worker   # worker/ is a separate npm package
npm run worker:dev        # signaling Worker (wrangler dev) on :8787
npm run dev               # Vite on :5173; proxies /room/* and /turn-credentials to :8787
npm run dev:https         # self-signed HTTPS so a phone on the LAN can be the studio's camera

npm test                  # Vitest unit tests (tests/**/*.test.ts, Node env)
npx vitest run tests/fight-simulation.test.ts       # single file
npx vitest run tests/collision.test.ts -t "facing"  # single test by name
npm run typecheck         # tsc for the app AND the worker
npm run build             # tsc --noEmit + vite build → dist/ (four entry points: game, studio, capture, about)

npm run test:signaling    # needs worker:dev running
npm run test:e2e          # needs dev + worker:dev; headless Chrome: game, studio (fake camera), /capture streaming to /studio over real WebRTC, editing
npm run test:e2e:gamepad  # needs dev; virtual gamepad
npm run generate:assets   # rebuild public/placeholders and public/sounds
npm run generate:announcer  # macOS say + ffmpeg: TTS stand-ins for missing public/announcer/*.mp3 (-- --force, or -- <ids>)
node scripts/generate-og-image.mjs  # needs dev; public/og-image.png (link preview) from the title screen
uv run --with onnx --with onnxruntime --with numpy python scripts/build-matting-model.py  # models/ for dev (needed by the studio)
```

E2E scripts use `playwright-core` with a local Chrome; set `CHROME_PATH` if Chrome isn't in `/Applications`. `test:e2e` accepts `-- <baseUrl> <screenshotDir>`.

CI (`.github/workflows/deploy.yml`) runs `typecheck`, `test`, `build` on every push, and on `main` deploys the Worker and the site (Cloudflare Pages). The site is built with `VITE_SIGNALING_URL=wss://…`.

## Architecture

```
src/shared/      fighter model, codec (.photodojo zip), IndexedDB storage (fighters, settings, drafts,
                 fighterSources), pose definitions/geometry, frame data, room codes, canvas helpers,
                 stick-figure skeletons
src/simulation/  the fight — pure TS, NO Phaser imports, fixed-timestep, deterministic
src/capture/     the capture pipeline modules (no UI): camera session, MediaPipe pose tracker, matcher,
                 framing, ghost overlay, ISNet background removal/matting, sprite normalizer, cut-out
                 quality, sharpness, sounds, voice prompts — used by the studio (the phone uses only
                 camera-session + sharpness)
src/studio/      the Character Studio (/studio): StudioApp, pure flow reducer, drafts, CameraSource
                 (LocalCamera / RemoteCamera), PhoneHost, edit sessions, DOM screens
src/phone/       the phone camera page (/capture): pure PhoneSession (protocol) + camera/DOM glue
src/transfer/    signaling client, peer connection (data channel + video track), camera protocol,
                 still sender/receiver with backpressure
src/game/        Phaser scenes, input sources, rendering
worker/          Worker + SignalingRoom Durable Object (≤2 sockets per room, rooms expire after 10 min)
```

Key boundaries that span files:

- **Simulation vs. rendering.** `FightSimulation.step([InputFrame, InputFrame])` (`src/simulation/fight-simulation.ts`) owns all game state. `FightScene` steps it at a fixed 60 Hz via an accumulator and only reads state to render — render code never mutates simulation state. Input sources (`src/game/input/`: keyboard, gamepad, training dummy) all produce `InputFrame`; the simulation never touches Phaser input. Keep it this way so rules stay unit-testable in Node.
- **Frame data and hitboxes come from landmarks.** `src/shared/frame-data.ts` defines each attack (startup/active/recovery, damage, hitstun/blockstun, hit level, which captured pose/variant to show) and derives hurtboxes, hitboxes and body boxes from each fighter's stored 33 MediaPipe landmarks — no hand-authored boxes. `src/simulation/collision.ts` transforms them to world space by position/facing. Changing fight rules generally means editing `frame-data.ts` / `fighter-state-machine.ts` and updating `tests/fight-simulation.test.ts` / `tests/collision.test.ts`.
- **Archetypes.** Every fighter has one (`Fighter.archetype`, `src/shared/archetypes.ts`), picked in the studio right after setup (so all sixteen poses then run in a row), which sets its one extra pose, `signature`, whose definition and stick skeleton depend on the archetype (`poseDefinition`, `stickPoseParams`). It adds one move on down + punch + kick to the shared core: brawler `charge` and acrobat `flyingKnee` are ordinary `ATTACKS`, grappler `bearHug` is a `GRABS` entry next to the throw, guardian `parry` is `PARRY` (a caught attacker goes `parried`). The simulation reads the archetype from `FighterGeometry.archetype`. Reach/hurtbox clamping for the signature pose uses that archetype's stick figure. Frame data and reasoning: `docs/fighting-mechanics.md` §3.4.
- **Fighter data flow.** A `Fighter` (`src/shared/fighter-model.ts`) is pose PNG blobs + landmarks + anchor + sounds. The studio saves it straight into IndexedDB (`fighter-storage.ts`, `saveFighterWithSources`) on the same computer as the game; no fighter goes over the network. `fighter-codec.ts` serializes it as a `.photodojo` zip (fflate) for export/import between computers (fighter select's Export / Import, `saveImportedFighter`). Fighter select's "Open the studio" and a tile's "✂ Edit" are page changes to `/studio` and `/studio?edit=<id>`; the studio's "Back to the game" goes to `/?to=select`, which `BootScene` honours, and the library is read fresh at every boot.
- **The studio and its camera** (`docs/character-studio.md`). `StudioApp` (`src/studio/main.ts`) runs the pipeline; its screens are driven by `studio-flow.ts` (pure reducer, Node-tested: setup → archetype → tips → loading → poses → review → sounds → preview → saving → saved, plus `camera` / `cameraLost` when no camera is ready). The camera is a `CameraSource` (`camera-source.ts`): `LocalCamera` (`getUserMedia` via `CameraSession`, with a device picker) or `RemoteCamera` (a phone's received track; `grabStill` asks the phone for a PNG still over the `camera` data channel). Live tracking runs on the video; every capture re-detects on the full-resolution still, and a remote still with nobody in it fails rather than falling back to live landmarks (different moments). `PhoneHost` keeps one room code for the whole visit, stops listening once a phone's channel opens (one phone at a time; the Worker itself would let a second guest replace the first), and reopens the same code when the phone drops or the room expires. The phone page (`src/phone/`) keeps retrying the same code until the studio sends `bye`. Protocol: `src/transfer/camera-protocol.ts` (JSON messages + binary still chunks with a request id and chunk index, `StillAssembler`), `still-sender.ts` / `still-receiver.ts` (backpressure via `bufferedAmountLowThreshold`). A camera switch on the phone is `replaceTrack`, never a renegotiation (signaling is closed by then). `/studio?debug=1` adds the matting debug export.
- **Fighter sources and editing.** Saving in the studio also writes the fighter's sources (`fighterSources` store, `DB_VERSION` 3: each pose's cut-out PNG + geometry, as a draft holds) so a retake can re-plan every sprite at one fighter-wide scale. They're deleted with the fighter, and when an import overwrites its id. `/studio?edit=<id>` (`edit-session.ts`) opens a saved fighter on the review: same id, `createdAt` and career record. Fighters without usable sources (imported, or from the old phone capture) can be renamed, get new sounds, or have every pose captured again, but not single retakes. Drafts (`src/studio/capture-draft.ts`, `DRAFT_VERSION` 3) resume an unfinished new fighter; edit sessions aren't drafted. `openFighterDb` closes on `versionchange` and reports `blocked` (`onDbBlocked`) so an old tab can't wedge an upgrade.
- **Signaling is same-origin in dev.** Pages connect to `/room/<code>` on their own origin (the studio is the host, the phone the guest); Vite proxies to the Worker so a phone only trusts one certificate. In production `VITE_SIGNALING_URL` points at the Worker.
- **Background removal** runs in the studio, on the computer (the phone runs no models: the pose models and ISNet together didn't fit in an iPhone tab). It is deliberately simple: one strong model and almost no post-processing. `background-remover.ts` runs ISNet (1024², via onnxruntime-web: WebGPU, falling back to WASM) on a crop around the skeleton; `matting.ts` keeps only regions connected to the skeleton. Don't add heuristic stages (mask fusion, hole filling, edge filters, empty-room photos): an earlier pipeline full of them ended up worse than the model alone. If cut-outs are bad, look at a better model first. The model files are built by `scripts/build-matting-model.py` (rembg's ISNet with MaxPool `ceil_mode` turned off, which WebGPU lacks; bit-identical output; plus an fp16 copy) into git-ignored `models/`, which the dev server serves at `/models/`. WebGPU with `shader-f16` runs the fp16 copy: a 1024² fp32 run takes ~2.4 GB in Safari (fp16 ~1.5 GB); WASM always gets fp32 (fp16 is ~5× slower there). Model memory still matters on iPads, which may open the studio (with a warning): that's why the matting session is built after the pose models, the downloaded bytes are dropped once ORT has them, and there's no warm-up run on iOS. They're too big for Pages (25 MiB per file), so production builds set `VITE_MATTING_MODEL_URL` and `VITE_MATTING_MODEL_FP16_URL` (without the latter, fp32 everywhere). ORT's ~28 MB WASM binary is likewise loaded from jsDelivr, not bundled (`onnxruntime-web-use-extern-wasm` condition in `vite.config.ts`; `ORT_VERSION` must match package.json). BiRefNet was tried and doesn't run in ORT Web without heavy graph surgery. `/studio?debug=1` exports the frame, model alpha and final alpha. Quality beats speed here: the heavy pose model is used everywhere and each capture takes the sharpest frame of a burst (`sharpness.ts`). Models are downloaded with progress and stored in the Cache API (`vision-runtime.ts`). Model URLs can be overridden with `VITE_POSE_MODEL_URL`, `VITE_MATTING_MODEL_URL`, `VITE_MATTING_MODEL_FP16_URL`.
- **Pose tweening is rendering only.** A `{ fromPoseId, toPoseId, frames }` sequence entry in `frame-data.ts` plays as `fromPoseId` in the simulation (boxes unchanged), and `SOFT_CUTS` lists cuts between actions that morph; `tweenOf` and `PoseTransitions` tell the renderer to ARAP-warp both captures onto an interpolated skeleton and cross-dissolve them, with moving limbs cut into their own mesh piece (`src/game/render/arap.ts`, `pose-tweener.ts`, `pose-transitions.ts`: pure and Node-tested; Phaser `Mesh` glue in `fighter-sprite-view.ts`, WebGL only). Idle sways into the `idle-2` capture. PLAN §9 has the details and limits. Hit weight (struck pose held through hitstop, both fighters shaking on a clean hit, colour-coded sparks at the hit event's `at`) is likewise render-only: `hit-feel.ts` / `hit-markers.ts`.
- **Stages are scenery only.** `src/game/stages/`: each stage is a `StageDefinition` (id, name, optional `preload`, `build` drawing into a container in screen space) in its own file, listed in `STAGES` (`stages.ts`); assets go in `public/stages/<id>/`. A stage's optional `music` (looping; list an Ogg and an MP3 fallback) is loaded and played through `stage-music.ts` (fights, and as a preview on stage select) at the player's Music volume, with an optional `credit` shown on stage select (also credit tracks on the About page). Lunar Dojo uses "Space-Time" by TomboFry. The menus (title, fighter select) share one unbroken track, "Get A Move On" by TomboFry (`src/game/menu-music.ts`). Music is licensed and NOT in the repo: tracks are named by file and resolved by `music-url.ts` against `VITE_MUSIC_BASE_URL` (an R2 bucket in production), defaulting to git-ignored `public/music/` in dev; missing files mean silence: menu scenes call `playMenuMusic`, the scenes that take over (stage select, controls, fight) `stopMenuMusic`. The floor, walls and stage width are fixed (`render/stage.ts`, the simulation), so stages can't change the rules. The chosen id rides in `FightSceneData.stageId`; with more than one stage, `startMatch` routes fighter select through `StageSelectScene` (with a Random option), otherwise straight on. The title demo picks a random stage.
- **Match stats** come from the simulation's events: `MatchStatsTracker` (`src/simulation/match-stats.ts`, pure and Node-tested) is fed every stepped state by `FightScene` (not replays) and handed to `MatchResultScene` at `matchOver`. The FIRST BLOOD / N HIT STREAK / PERFECT callouts come the same way from `CalloutTracker` (`src/simulation/callouts.ts`, sharing `HitStreak` with the stats). A hit streak is clean hits in a row, not a true combo (the frame data rules those out): it ends when the opponent lands a hit or throw, or blocks, parries or breaks a throw, and at each round start. Between rounds it's `RoundResultScene`. Each finished match (not practice) is also added to both fighters' career records (`src/game/fighter-records.ts`, settings key `fighterRecords`, by fighter id), shown on fighter select (with the two picks' head-to-head from `versus`), the match result, and `FighterStatsScene` (ready + down on fighter select, or click the record). Per-move clean hits come from `PlayerStats.movesLanded`.
- **Renaming** a captured fighter is `RenameScene` (`rename-scene.ts`, opened from the selected tile's ✎): it reads the browser's own keydown events, not Phaser's, because Phaser replays a frame's earlier key events when several land in one frame. Names go through `tidyFighterName` (`MAX_TYPED_NAME_LENGTH`, shared with the studio's name field). The archetype can't be changed on fighter select: the signature photo is that archetype's pose. Editing in the studio can change it (that retakes the signature pose).
- **Playing alone.** On fighter select, a lone player who has picked presses punch to open the empty slot as the CPU (`CpuSlot` in `character-select-scene.ts`): their controller picks its fighter, then Match (CPU level) or Practice. A match against the CPU is an ordinary fight with `inputs[1] = { kind: "cpu", level }` (a non-player `InputDescriptor`, like practice's `{ kind: "dummy" }`): `FightScene` drives it with `DummyInputSource` at that CPU level, the controls screen shows its half as ready, and it isn't added to career records. Up instead of punch still starts the tutorial.
- **Party modes (series)** are menus only: tournament (`src/game/tournament.ts`, single-elimination bracket) and king of the hill (`src/game/king-of-the-hill.ts`, winner stays on), both pure and Node-tested. Fighter select (T / Start, both players joined) → `SeriesSetupScene` (pick the mode and 3–8 fighters) → the mode's own scene between matches (`TournamentScene` / `KingOfTheHillScene`, scene key = `SeriesKind`). The `SeriesSession` (`src/game/series.ts`) lives in the registry (`REGISTRY.series`); each match is an ordinary fight with `FightSceneData.series` set, so backing out (`menuSceneFor`) and the match result return to the mode's scene, and the result is recorded with `recordSeriesResult`. A new mode = a pure rules class with `record(side)`, a `SeriesKind`, its `SERIES_INFO`, and a scene.
- **Round intro handshake.** Every fighter captures a `handshake` pose (last in the capture order). During the intro `FightSimulation` scripts both fighters (`introStep`, timeline `INTRO` in `round-rules.ts`): walk in from the start positions, pause, player 1 offers a hand, player 2 takes it, shake, walk back. `src/shared/handshake.ts` turns each arm about its shoulder so both hands meet at one height (`handshakeGrips`) and gives the reach the simulation uses to stand them so the hands overlap. The pumping hand is render-only: variants 1/2 of `handshake` are stand-ins (the capture warped onto a raised/lowered hand, `shakenGrip`) that `FighterSpriteView` tweens between.
- **Announcer.** Every line is listed with its text in `src/game/announcer-lines.ts` (`ANNOUNCER_LINES`, plus the pure pickers: round start / final round, K.O. / double K.O. / time, hit streaks, match winner, stage names, tournament rounds; Node-tested) and is a file `public/announcer/<id>.mp3`. The committed files are text-to-speech placeholders (`generate:announcer`, which never overwrites an existing file unless asked) meant to be replaced by recorded takes; a missing file is silence. `announce()` (`announcer.ts`) keeps one voice: a new line cuts the last off unless `queue`d (PERFECT after K.O.), skips lines while the browser still holds sound back, and plays at the "Announcer volume" setting. A new line = an entry in `ANNOUNCER_LINES`, then `generate:announcer`; a new stage gets a `stage-<id>` line.
- Stick-figure skeletons in `src/shared/stick-figure.ts` double as built-in placeholder fighters (red, blue, green, purple: `PLACEHOLDER_IDS`, drawn by `generate:assets`), capture ghosts, and synthetic landmarks for tests (see `tests/helpers.ts`).

## Conventions

- Tests run in Vitest's `node` environment by default; tests needing IndexedDB use `fake-indexeddb`, and `happy-dom` is available for DOM bits.
- `tsconfig.json` is strict with `noUnusedLocals`/`noUnusedParameters`; the worker has its own `tsconfig.json` and TypeScript version.
- Every captured pose keeps all 33 landmarks: ARAP tweening (PLAN §9) warps with them — don't drop them from the model or codec.
